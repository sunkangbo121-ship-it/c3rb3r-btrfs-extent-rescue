# 02 · 内存采集与密钥扫描：为什么这个 NO_MATCH 可信

结论先放前面：**本案没有从内存里拿到密钥，而且这个「没有」是可信的。** 采集完整（0 不可读页），扫描器先通过了埋钥自检，时间线也解释得通——加密器在约 27 小时前就退出了，而样本在退出路径上会主动清零 48 字节主密钥缓冲（soimy 逆向结论）。

这一篇的价值在方法：在一台不能装内核模块、不想在被害卷上写任何东西的 DSM 上，**5 分钟内**把 16 GB 内存拉回来并扫完。

## 一、采集：`/proc/kcore` → LiME，经 SSH 流式回传

### 为什么不用 AVML / LiME 内核模块

- DSM 7.2.1 的内核是 5.10.55+，没有对应头文件，编 LiME 模块不现实；加载不匹配的模块有让机器崩溃的风险。
- AVML 是现成二进制，但要先把它传到 NAS 上、通常还要写到本地盘。我们希望**被害机上一个字节都不写**。
- DSM 自带 Python 3.8，`/proc/kcore` 可读（root），这就够了。

### `tools/kcore_dump.py` 做了什么

1. 读 `/proc/kcore` 的 ELF 头，取所有 `PT_LOAD` 段中 `p_paddr` 有效的那些。
2. 内核直接映射区（direct map）里所有物理内存段的 `vaddr − paddr` 是同一个常数；内核代码段等其他映射不是。取出现次数最多的那个差值，只保留它对应的段——这样得到的就是物理内存本身，不重复、不混入 vmalloc 等区域。
3. 每段先写一个 32 字节 LiME 头（magic `0x4C694D45`、物理起止地址），再按 4 MiB 块 `pread` 段内容写到 stdout。
4. 某块读失败时退化为逐页读，读不到的页填零并在 stderr 记一条 `HOLE`，最后报告不可读页数。

```sh
ssh USER@NAS_IP 'sudo python3 - --list' < tools/kcore_dump.py         # 只列段
ssh USER@NAS_IP 'sudo python3 -' < tools/kcore_dump.py > ram.lime 2> dump.log
```

脚本从 stdin 送进去，镜像从 stdout 回来，NAS 上不留文件。

### 本案结果

| 项目 | 值 |
|---|---|
| 物理内存 | 16 GB 机器，direct map 共 **15.86 GiB，5 段** |
| 不可读页 | **0** |
| 速度 | 约 100 MB/s（千兆局域网 + SSH），约 3 分钟 |
| zram | 已用约 860 MB，**未单独采集** |

关于 zram：被换出到 zram 的页在物理内存里是**压缩后**的形态，直接扫物理内存看不到其中的明文。lllong1377 的案例专门采了 zram。本案没采，这是一个覆盖缺口；但考虑到下文的时间线（进程退出时主动清零），我们判断它不改变结论。下次建议同时 `dd` 出 `/dev/zram*`（只读）。

## 二、扫描：`tools/keyscan.c`

### 被找的东西

沿用 soimy 的格式分析：

```
footer[0:48] = AES-256-CBC(key = master[16:48], iv = master[0:16]) of  file_key(32) | nonce(8) | nonce(8)
```

第三个密文块解密后是 `nonce || nonce`，而 CBC 下 `P3 = D_k(C3) XOR C2`，与 IV 无关。所以对内存里任意 32 字节候选 `k`：

```
P3 = AES256_ECB_decrypt(k, footer[32:48]) XOR footer[16:32]
P3[0:8] == P3[8:16]   →  k 就是会话 AES 密钥（64 位校验）
```

误报期望：45 亿候选 × 3 个页脚 × 2⁻⁶⁴ ≈ 7×10⁻¹⁰，等于零。命中时同时打印候选前 16 字节（`iv16|key32` 布局下就是 IV），供后续完整 CBC 复核。

### 实现要点

| 项目 | 做法 |
|---|---|
| 步长 | **1 字节**，全偏移，不做对齐假设 |
| 前置过滤 | 滑动窗口统计 32 字节里的不同字节数，**≥ 22** 才做 AES。随机 32 字节的期望不同字节数约 30.1，被误滤的概率约 7×10⁻⁸ |
| AES | macOS CommonCrypto（`CCCryptor`，ECB，硬件 AES） |
| 并行 | 每段切成 256 MiB 的作业，10 线程 |
| 页脚 | 同时测 3 个不同文件的 `footer[0:48]` |
| 输入 | 直接 `mmap` LiME 文件，按 LiME 头还原物理地址 |

### 本案结果

| 项目 | 值 |
|---|---|
| 扫描量 | 15.86 GiB，5 段，68 个作业 |
| 实际做 AES 的候选 | **4,506,484,020**（约 4.5×10⁹，占全部偏移的 26%） |
| 线程 | 10 |
| 耗时 | **4 分 45 秒** |
| 结果 | **NO_MATCH**，`hits.txt` 为空 |

## 三、「没找到」之前先证明「找得到」

完全照搬 lllong1377 的原则：**扫描器必须先证明自己能找到，才有资格宣布没找到。**

本案正式扫描前用一份 8 MiB 单段合成 LiME 镜像 + 2 个页脚做了自检：随机生成主密钥，用它包一条合法记录作为页脚，把 `iv16|key32` 埋进镜像，要求 keyscan 命中。通过后才跑正式镜像。

为了公开，我们把自检生成器整理成 `tools/make_selftest.py`，并加了负对照，发布前在分析机上复跑：

```
$ python3 tools/make_selftest.py selftest 8
$ ./keyscan selftest/planted.lime selftest/footers.bin 4
HIT footer=0 off=<与 expect.txt 一致> ...          ← 恰好 1 行，且是用真主密钥包的那个页脚
$ ./keyscan selftest/blank.lime selftest/footers.bin 4 | wc -l
0                                                  ← 负对照 0 命中
```

自检覆盖了：LiME 头解析、非对齐偏移、前置过滤不误杀真密钥、多页脚中只命中正确的那个。

## 四、NO_MATCH 的解释

按 lllong1377 列的四种解释逐条排除：

| 解释 | 本案 |
|---|---|
| 采样窗口没赶上 | **是主因。** 最后一批加密 10/28 ~20:02，采集 10/29 ~23:28，相隔约 27 小时；采集时 `/proc` 中已无加密器进程 |
| 样本不同 / 布局不同 | 页脚布局与 soimy 一致，扫描用的是本会话自己的页脚，排除 |
| 镜像不全 | direct map 全部 5 段、0 不可读页；zram 未采是已知缺口 |
| 扫描器有问题 | 自检通过，排除 |

和 lllong1377 的结论一样：**该看的是加密进程还在不在，不是机器有没有重启过。** 本案 uptime 23 天，从未重启，照样没有密钥。

## 五、如果你扫到了：soimy 解密器的一行改动

soimy 的 `decrypt_copy.py` 把会话标记写死为 `ce35a593`，用在别的会话上会被页脚检查拒绝（这是正确的保护）。本案准备了一个只改一行的本地版本，让标记可通过环境变量配置，默认值不变：

```diff
-MARKER = bytes.fromhex("ce35a593")
+MARKER = bytes.fromhex(os.environ.get("C3RB3R_MARKER", "ce35a593"))
```

使用时 `C3RB3R_MARKER=0b5c8e4c python3 decrypt_copy.py …`。文件版权与授权归 soimy，本仓库**不收录**该文件，请从[上游](https://github.com/soimy/c3rb3r-rescue)获取后自行修改。本案没拿到密钥，这个改动**未在本案的真实数据上验证过**。

## 六、经验

- `/proc/kcore` + 标准库 Python 是 DSM 上最省事的整机采集方式，不需要任何外部二进制或内核模块。
- 采集 3 分钟、扫描 5 分钟，成本很低，**进程已退出也值得做一次**，但要对结果有正确预期。
- 真正决定成败的是发现时间。本案如果在 10/28 下午发现，加密进程还在跑，走 soimy / Benjamin-zlt 的进程内存路线大概率能全解。
