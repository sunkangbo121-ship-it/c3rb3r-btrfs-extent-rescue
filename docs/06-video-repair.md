# 06 · 部分恢复视频的修复

bookend 合成之后，`0x25` 分段加密的大文件里仍有约 100 个「部分恢复」：三段加密区中有一段或几段的原 extent 已被释放、覆盖，缺口填了零。对照片这通常只是一块灰，对视频却往往是**整个文件打不开**——因为丢的恰好是视频的索引。本篇记录把这类视频救成「能完整播放」的方法和实测结果。

## 一、为什么视频比照片更脆弱

`0x25`（pct=10）加密文件头、正中、文件尾三段，各占 4%：

- **手机录的 MOV（iPhone 等）把 `moov` 索引写在文件末尾。** 尾段一丢，`ftyp`、`mdat` 都在，但没有索引，播放器不知道每一帧在哪里，直接拒绝打开。
- **很多 Android / 云台相机的 MP4 把 `moov` 放在文件开头（faststart）。** 头段一丢，连 `ftyp` 和 `mdat` 头一起没了。
- 文件越大，4% 越长：一个 5 GB 的视频每段约 200 MB，超过 btrfs 单个 extent 的 128 MiB 上限，**必然有整块 extent 完全落在加密段里**，没有剩余明文引用它，于是被释放。这就是大视频部分恢复比例明显偏高的原因。

## 二、修复流程

全部只读源卷；中间结果写另一个卷；最终校验在 macOS 上用 AVFoundation 完成。

### 1. 找回尾部 `moov`（`videofix.py`）

`moov` 的偏移和长度可以从现存数据推出来：`moov` 紧跟在 `mdat` 后面，`mdat` 头还在，所以 `moov_off = mdat 起点 + mdat 长度`，`moov_size = 文件长度 − moov_off`。于是在原文件已知 extent 附近的裸设备上搜 `be32(moov_size) + "moov"` 这 8 个字节，**命中几乎是唯一的**。

实测：被释放的尾部 extent 常常就在主 extent 物理位置后面几十 KiB（本案一例是紧随其后 32 KiB）。找到后把这块按连续区读回，补进文件尾部。

### 2. 逐帧校验，只留可证实的字节（`movsamples.py`）

H.264 / HEVC 在 MP4/MOV 里是「4 字节长度 + NAL」的序列，**一个样本里所有 NAL 长度加起来必须正好等于样本大小**，且每个 NAL 头的禁止位为 0。这是一个很强的逐帧校验：

- 用 `moov` 里的 `stsz`/`stco`/`co64`/`stsc` 算出每个视频样本的偏移和大小；
- 对补回区间里的每个样本做长度框架检查；
- 只保留「到 `moov` 为止都校验通过」的最长后缀，其余清零。**宁可留空，不留来路不明的字节。**

### 3. 跳过坏段、无损拼接（`finish_videos2.py` + `splicevideo.swift`）

剩下的坏帧不能靠截断处理——坏段在中间时，截断会把后半段一起扔掉。做法：

1. 由坏帧算出时间段，并延到下一个关键帧（`stss`），因为坏关键帧之后的 P/B 帧都解不出来；
2. 用 `AVMutableComposition` 把好时间段按顺序插入，`AVAssetExportPresetPassthrough` 导出——**不重新编码，画质与原片相同**；
3. 用 `checkvideo.swift` 对每条轨道单独建 `AVAssetReader`、解码全部视频帧和音频样本；
4. 仍有解码失败：若失败时间落在某个加密段对应的时间范围内，**整段跳过**（这段读回的字节框架合法但内容可疑）；否则在失败点前后多跳几秒；最多 25 轮；
5. 都不行才退回到「截到第一个坏点」。

两个容易踩的坑：

- iPhone 视频常带**两条音频轨**。按媒体类型做字典键会让一条覆盖另一条，坏的那条被「藏」起来。要按 track ID 分别检查。
- 中段加密区读回的字节可能**通过长度框架检查但解码失败**。只做框架检查会误判；必须以完整解码为准，再按加密段整体跳过。

### 4. 头部整段丢失：重建文件头（`headerfix.py`）

`ftyp` 和 `mdat` 头都没了时，先找 `moov`：要么还完整地在文件末尾，要么在裸设备上搜 `"moov" + mvhd` 特征。候选 `moov` 必须通过验证——用它的样本表去核对文件里**仍为明文**的那部分帧，**80% 以上的帧长度框架对得上**才接受，避免把别的视频的索引装错。然后在第一个 chunk 前写入 `ftyp` + `free` + `mdat` 头，把 `moov` 接到文件末尾（atom 顺序不影响播放，样本偏移是绝对的，不用改）。

### 5. 兜底：Synology Photos 的转码版

Synology Photos 会为每个视频在 `@eaDir` 下生成一份低码率转码（`SYNOPHOTO_FILM_H.mp4`）。它也被加密了，但通常在 5 MiB 以上，同样是 `0x25`，用同一套 bookend 方法就能完整取回。原视频实在修不好时，用它代替，并在文件名里标明是低画质版。

### 6. 试过但没用：逐帧在裸设备上找回中段数据（`gapfill.py`）

思路：大多数帧是单个 NAL，长度前缀 = 样本大小 − 4；btrfs 数据 extent 在文件内和逻辑地址上都按 4 KiB 对齐，所以 `逻辑地址 % 4096 == 文件偏移 % 4096`。用这两个约束在附近搜每一帧，再用后续帧确认映射。

实测：在测试视频上**一帧都没找到**（±512 MiB 内），每个文件还要扫 5–10 分钟。说明完全落在加密段里、被释放的 extent 基本都已被后续写入覆盖。列在这里，免得后来者重复。

## 三、实测结果

| 环节 | 结果 |
|---|---|
| `0x25` 部分恢复的文件 | 102 个（其中视频约 100 个；32 个 >1.5 GiB 的大视频里 29 个属于这一类） |
| 尾部 `moov` 搜回（±512 MiB） | 中小视频 72 个中找回 35 个，另 10 个本来就带 `moov`；扩大到 ±4 GiB 没有新增 |
| 头部整段丢失的大视频 | 18 个，重建成功 2 个（1 个 `moov` 在文件尾，1 个从裸设备找回） |
| 最终可完整播放的修复版 | 47 个；保留时长中位数约 98%，其中 42 个保留 ≥ 90% |
| 改用低画质转码版 | 35 个（转码版本身 84/89 个可完整取回；2 个转码版也经过跳段拼接） |
| 验证 | 每个输出文件都在 macOS 上逐轨道完整解码通过；另抽查 8 个 bookend 完整恢复的视频，8/8 完整解码 |

剪掉的部分都是加密段对应的几秒到几十秒；拼接点处会有一次跳跃，没有做任何画面插补。

## 四、局限

- **修复版不是原片**：缺的那几秒就是没有了，只是让剩下的部分能放。
- 跳段依据的是解码器是否报错。解码通过不等于每一帧都和原片一致——中段读回的字节如果混入了别的视频数据，有可能「能解但画面不对」。本案对抽样做了目视检查，没有逐帧比对。
- `headerfix.py` 写的 `ftyp` 是通用值（`qt` / `mp42`），不是原值；不影响播放。
- 工具只覆盖 AVC/HEVC 长度前缀格式；其他编码（ProRes 等）需要另外的逐帧校验方法。
