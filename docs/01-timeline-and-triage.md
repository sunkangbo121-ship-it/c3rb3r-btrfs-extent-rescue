## 分诊发现

### 加密器：已退出，无持久化

- `ls -l /proc/*/exe | grep deleted` 只找到 5 个 root `inetd`，可执行文件是一个已被删除的 busybox，启动时间等于开机时间。这是黑群晖引导器带起来的 telnet 服务（23 端口，监听 `0.0.0.0`），**不是加密器**，但它本身是严重暴露面。
- 没有 `/bin/libgld`、`/bin/qnetd`；没有 `/etc/cron.d/synot*` 一类持久化。`/etc/cron.d` 目录 mtime 是 10/29 04:47，逐个看了**内容**，都是正常任务。（[lllong1377 的案例](https://github.com/lllong1377/c3rb3r-never-rebooted-still-no-key/blob/main/docs/04-iocs.md)提醒过：持久化会伪装成正常文件名并自我重建，所以看内容，不看名字。）
- 没有到外部地址的 ESTABLISHED 连接。

### 样本：与已公开会话不同

- 页脚会话标记 `0b5c8e4c`，全部 24,142 个文件一致；加密模式全部 `0x20`（真加密，不是诱饵）。
- 页脚布局与 soimy 公开的格式逐字段一致。
- 已公开会话标记：`ce35a593`、`883c0309`、`038c0ac9`、`6d147f60`，本案与它们都不同，**soimy 公开的会话候选不适用**（试用无效）。

### 平台：为什么 btrfs 这条路走得通

| 项目 | 值 | 对恢复的意义 |
|---|---|---|
| 文件系统 | btrfs，`space_cache=v2`、`syno_allocator`、`auto_reclaim_space` | 写时复制：改写会写到新位置，旧 extent 不原地覆盖 |
| 存储栈 | md → LVM → flashcache-syno（DUMMY）`cachedev_N` → btrfs | `cachedev_N` 已挂载，`btrfs restore` 拒绝；底层 LV 内容相同，可只读访问 |
| 空间 | 7.26 TiB，已用约 4.9 TiB，未分配约 2.3 TiB | 新写入有大量空闲区可去，被释放的旧 extent 不一定立刻被复用 |
| 运行状态 | 未重启，停写入及时 | 旧 extent 没有被 balance/defrag 搬走 |

对比：lllong1377 的卷数据区 100% 占满，被释放的旧块早已被吃掉。**同一个家族、同一种加密方式，能不能救取决于卷的状态。**

### 目标目录：页脚普查

对目标照片目录全部 `.L0CK3D` 读末尾 588 字节（`tools/collect_footers.py`）：

| 文件模式 | 含义 | 文件数 | 体积（含页脚） | 原始大小范围 |
|---|---|---|---|---|
| `0x26` | 仅加密前 1 MiB，原地改写 | 10,220 | 26.9 GiB | 约 1–5 MiB |
| `0x25` pct=10 | 头、中、尾各加密 4%，原地改写 | 7,197 | 345.0 GiB | 5 MiB 以上，最大约 9.5 GB |
| `0x24` | 整文件加密 | 6,725 | 3.1 GiB | ≤ 1 MiB |
| 合计 | | **24,142** | **375.0 GiB** | |

按大小分档很清楚：≤1 MiB 整文件、1–5 MiB 只加密开头、更大的分三段。照片库里大量缩略图/小图落在 `0x24`，原图和视频落在 `0x26`/`0x25`。

**这张表决定了后面所有的预期**：72% 的文件、99% 的字节属于原地部分加密，是 btrfs 能救的类型；`0x24` 文件数不少，但总共只有 3.1 GiB，而且几乎救不回来（见 [03](03-btrfs-extent-retention.md)）。

## 立即止损

1. 停掉所有会往该卷写数据的套件：相册、Drive、Cloud Sync、Download Station、Surveillance Station（`/usr/syno/bin/synopkg stop`，全路径）。
2. 保持机器开机，先取整机内存（[02](02-memory-capture-and-keyscan.md)），再做任何可能改变内存状态的事。
3. 所有输出写到**另一个卷**；对被加密卷只读。
4. `.L0CK3D` 原件一个不动。
