## 三、验证等级

沿用 soimy 的[结果等级](https://github.com/soimy/c3rb3r-rescue/blob/main/skills/dsm-ransomware-rescue/references/inventory-verify.md)用语，诚实标注本案停在哪一级：

| 等级 | 本案是否达到 | 说明 |
|---|---|---|
| 历史 SHA 完全一致 | **否** | 没有原文件摘要可比 |
| 完整归档/压缩检查 | 部分（仅抽样图像） | 40 张随机抽取的恢复图片由 macOS ImageIO 完整解码，**40/40 成功**，并逐张目视检查，未见异常。图像解码读完整个码流，相当于对图像的「完整格式检查」 |
| 语法或文件头 | **是（全部）** | 每个 OK 文件的前若干字节符合 JPEG / PNG / HEIC / MOV / MP4 等格式签名 |
| 应用验收 | 否 | 尚未导回相册应用重新索引 |
| 失败/未决 | FAIL、BIG 列为未决 | 不计入成功 |

说清楚：**文件头正确 ≠ 内容正确。** 对 `0x26` 和 `0x25` 来说，被恢复的字节来自仍处于分配状态的原 extent，可信度高；但对 `0x24`，读回的 extent 已被释放过，文件头像样只说明开头那几个字节没被覆盖，后面可能已混入别的数据。视频只做了文件头检查。

## 四、不声称什么

- **没有恢复密钥。** 本案所有恢复都不经过解密。
- **`0x24` 小文件大部分已丢失。** 6,725 个中只有 290 个找到攻击前引用，其中中期 56 / 177 通过文件头检查；这些读回的 extent 已被释放过，**文件头检查不能证明内容**。
- **不是逐字节证明。** csum tree 校验尚未做（建议做法见 [03 第六节](03-btrfs-extent-retention.md#六可以做得更好用-btrfs-数据校验和做逐块验证)）。
- **整 extent 合成是一个假设**：攻击前该 extent 从 `foff − eoff` 开始整块属于这个文件。对顺序写入的照片和视频成立，对被多次改写、做过 reflink/去重、或多个文件共享 extent 的情况不一定成立。
- **依赖卷的状态。** 能救多少取决于：卷有没有足够空闲空间（本案约 2.3 TiB 未分配）、写入方停得够不够快、期间有没有 balance/defrag/空间回收。lllong1377 的卷 100% 占满，同样的方法在那里几乎无用。
- **只适用于 btrfs 的写时复制。** ext4 等原地覆盖的文件系统没有这种残留；NOCOW 文件也没有。
- 恢复结果和原文件逐字节一致与否，本案无法给出结论；也不声称恢复了照片目录以外的数据。

## 五、改进方向

1. **csum tree 逐块校验**：遍历 csum tree，对读回的每 4 KiB 比对 crc32c，把验证等级从「文件头」提升到「btrfs 写入时的原文」。
2. **流式版 `extract_jobs`**：处理 >1.5 GiB 的 32 个文件，按段读写，不把整个文件放进内存。
3. **`0x24` 的更严格判定**：结合 csum、或图像完整解码，把「文件头像样」与「内容可用」分开统计。
4. **与 `btrfs restore` 结果合并去重**，给出按文件和按字节的总恢复比例。
5. **zram 一并采集**，补上内存覆盖缺口。
